### A3b architecture correction — raw temporary fd ownership

Architecture review found that the first A3b write path assigned the result of
exclusive `os.open` directly into local flow without separately tracking raw fd
ownership. If post-create `fstat` or `fdopen` failed, `stream` remained `None`
and the raw descriptor could stay open. On Windows that open descriptor could
also prevent safe temp cleanup.

The corrected write path now initializes an explicit raw-fd sentinel, owns the
descriptor immediately after exclusive creation, and transfers ownership only
after `fdopen` succeeds. The sentinel is cleared at that exact transfer point,
so the stream path and raw-fd path cannot double-close the same descriptor. On
any exception before transfer, the store closes the raw fd before considering
temp cleanup.

When `fdopen` fails, post-create `fstat` has already produced a trusted inode
identity. The correction therefore closes the raw fd, revalidates that exact
owned temp, removes only it, preserves the old target byte-for-byte, and leaves
unrelated files unchanged.

When the initial `fstat` itself fails, no trustworthy identity exists with
which to prove that the random pathname still denotes the just-created inode.
The store closes the raw fd and returns fixed I/O, but deliberately does not
unlink by pathname guess. The deterministic regression test therefore expects
one closed, randomly named residual temp inside the already validated runtime
directory, while proving the old target and unrelated file are unchanged. A
later explicit operator cleanup may inspect such a residue; the store does not
broaden or automate deletion without identity evidence.
